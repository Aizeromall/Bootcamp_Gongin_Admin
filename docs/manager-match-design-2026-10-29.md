# 매니저 경기 화면과 결과 조회

작성 일 : 2026-10-29 / 작업자 : 양태건

## 적용 화면

- 매니저 메뉴는 `내 매치 / 실력매칭 / 팀매칭`입니다. 평가 메뉴는 복원하지 않습니다. 본사 팀 관리 메뉴는 변경하지 않습니다.
- 세 화면에 `전 종목 / 축구 / 배구 / 농구 / 야구` 필터를 적용합니다. UI 순서와 서버의 종목 코드 순서는 별개입니다.
- 내 매치는 오늘 이후 모든 예정 경기를 기본 조회하고 달력·이전/다음으로 특정 날짜를 조회할 수 있습니다. 과거 날짜 제한은 유지합니다.
- 실력매칭과 팀매칭은 각각 해당 유형의 완료 결과만 조회하며 날짜별 일정과 별개로 모든 저장 결과를 최신순 표시합니다.
- 넓은 화면에서는 흰 목록·밝은 회색 상세, 작은 화면에서는 목록 선택·상세 복귀 방식입니다.

## 내 매치

실력매칭을 선택하면 상세 영역 안에서 경기 정보·출석 안내·예약자 명단·현재 레벨·포지션·예약번호·출석을 표시합니다. 전원 출석은 기존 attendance 명령을 회원별로 순차 호출하고 실패 시 중단합니다. 실제 서버 성공 응답으로만 출석을 갱신합니다. 팀 배정·4종목 기록·부상·결과 등록 동작을 유지하며, 등록 후 실력매칭 결과로 이동합니다.

출석 안내 문구는 현장 안내입니다. 자동 푸시 전송이나 목업 시간 이동 기능은 구현된 것처럼 표시하지 않습니다.

팀매칭 예정 경기에는 현재 팀원 명단을 조회합니다. 현재 팀원 명단은 출전·출석 확정 명단이 아닙니다. 기존 팀 API에는 출석·실시간 진행 상태 명령이 없어 이 부분을 저장한 것처럼 처리하지 않습니다. 팀 경기 출석과 경기 시작은 이번 읽기 전용 보완 범위에서 미구현입니다.

## 결과 표시

- 실제 저장된 스코어, 등록 담당자, 종목별 스탯 표와 회원별 현재 점수·현재 레벨을 표시합니다.
- 레벨은 기존 백엔드 rating_tier 기준을 사용합니다. 출석 화면은 `/match/rating/stat_keys`의 서버 등급 구간을 사용합니다.
- 개인 경기별 점수 변동은 기존 서버 완료 캐시에 해당 담당자의 rating_changes가 남아 있는 경우에만 반환합니다. 없으면 null이며 `변동 기록 없음`으로 표시합니다.
- 현재 점수에서 과거 경기의 전후 점수를 역산하지 않습니다. 재등록으로 점수 변동을 조회하지 않습니다.
- 팀별 요약은 저장된 승무패·스탯 합계·현재 팀 점수입니다. 과거 팀 점수 변동은 저장되지 않아 임의 ±점수를 만들지 않습니다.
- 해석할 수 없는 과거 스탯·스코어는 원문으로 보존합니다. 없는 점수나 스탯을 0으로 만들지 않습니다.

## DB 변경 없이 추가한 조회 API

`python/FastAPI/match/manager_result_search.py`를 `python/main.py`에 등록했습니다. 모든 경로는 require_manager를 통해 인증된 매니저를 사용하며, 클라이언트가 다른 담당자 ID를 지정하지 않습니다.

| 경로 | 내용 |
| --- | --- |
| `GET /match/manager/upcoming` | 오늘 이후 예정 실력매칭·팀매칭. 실력매칭의 취소·구장대여 예약은 제외 |
| `GET /match/manager/results?kind=pickup\|team&e_code=...` | 본인이 등록한 완료 결과 목록. e_code 생략 시 전체 종목 |
| `GET /match/manager/results/{code}` | 같은 담당자 조건으로 회원별 기록·현재 점수·팀 요약 조회 |
| `GET /match/manager/teams/{code}/roster` | 배정된 팀 경기의 현재 팀원 명단. 출석 API가 아님 |

운영 목록에는 기존 구장 코드·정원·종료 시간·예약자 종목 정보를 추가했습니다. 팀 매칭 응답에는 두 팀의 실제 종목이 일치하는 경우에만 e_code를 제공합니다. 이름이나 주소로 종목을 추측하지 않습니다.

신규 조회 라우터는 SELECT만 실행합니다. 실제 DB·테이블·컬럼·인덱스·데이터는 변경하지 않았습니다. 기존 결과 등록 API와 실제 서버를 실행하지 않았습니다. 앱 실행 시에는 새 라우터가 반영된 백엔드를 사용해야 합니다.

## 검증

- Flutter 전체 테스트 83개 통과. 결과 유형·종목 쿼리·현재 레벨·미보관 변동·오류 재시도·빈 목록·작은 화면·담당자 범위·전체 경기 진행 흐름을 Mock으로 확인.
- Python 결과 조회 단위 테스트 8개, 기존 경기 운영 단위 테스트 24개 통과. 실제 DB 연결을 Mock 처리하거나 순수 함수만 실행.
- flutter analyze: 기존 snake_case 이름 안내 35개. 새 오류·경고 없음.
- git diff --check 통과.
- Mock 데이터를 렌더링하여 넓은 결과 화면을 확인. 실제 서버·기기 및 실제 팀 경기 출석·시작은 미검증/미구현 범위로 구분.

`integration_match_flow.py`는 실제 DB 쓰기가 있어 실행하지 않았습니다.

## 500 오류 보완 — 2026-10-29

사용자가 수정한 실제 DB 구조를 읽기 전용 트랜잭션으로 확인했습니다. reservation에 r_cancel_date(datetime)가 추가되어 취소 조회의 기존 컬럼 참조를 유지했습니다. canceled_count 컬럼도 존재하지만 화면의 경기별 취소 건수는 기존 COUNT 집계 계약을 유지합니다.

연결 기본 정렬 규칙은 utf8mb4_0900_ai_ci이고 경기 코드 컬럼은 utf8mb4_unicode_ci여서, manager_result_search.py의 숫자 경기코드 CAST 비교 두 곳에서 MySQL 1267 오류가 재현됐습니다. 해당 변환 표현식에 CHARACTER SET utf8mb4와 COLLATE utf8mb4_unicode_ci를 명시했습니다. 테이블·컬럼·연결 설정 자체를 바꾸지 않았습니다.

존재하지 않는 진단 ID와 읽기 전용 연결을 사용하여 예정 경기·경기 결과·담당 구장 취소 SQL이 모두 오류 없이 실행됨을 확인했습니다. 실제 담당자의 기록을 조회하거나 DB를 쓰지 않았습니다. 결과 조회 Mock/단위 테스트 8개와 git diff --check가 통과했습니다. 실행 중 서버는 임의로 재시작하지 않았으므로 수정 코드 반영은 해당 서버의 재시작 또는 기존 자동 재로딩 후 확인해야 합니다.
