# 2026-10-28 백엔드 변경 대응

작업자 : 양태건

현재 관리자 저장소의 `8405e61`까지 반영된 코드와 로컬 작업 내용을 기준으로 비교했습니다. 이번 프론트 작업에서는 Python이나 실제 DB를 변경하거나 실제 취소 요청을 실행하지 않았습니다.

## 연결한 조회

- 본사 `매치 관리 → 팀 대 팀 매칭`: `GET /match/team_match`의 `status`, `keyword`와 `/match/team_match/{team_code}`를 연결했습니다. 실제 매치 코드로 상세를 조회하며 홈·원정 팀, 경기 일시·구장·매니저·서버 상태·결과·현재 팀장·팀 전적을 표시합니다. 결과가 없으면 0:0으로 만들지 않습니다. 개인별 골·도움·슈팅은 API에 없어 표시하지 않습니다.
- 본사 `매치 관리 → 취소 경기`: `GET /match/cancel?r_c_category=...`, `/match/cancel/{g_code}?r_date=...&rs_time=...`를 연결했습니다. 예약자·출석과 취소 기록을 조회합니다. `is_refunded`는 결제 기록 유무 기준이므로 실제 PG/계좌 환불 완료라고 표시하지 않습니다.
- 매니저 `지난 매치 → 담당 구장 취소`: `GET /match/manage/cancel/{로그인한 m_id}`만 사용합니다. 본사 전체 취소 상세 API를 매니저 화면에서 호출하지 않습니다.
- 취소 사유 문자열 `'1'`, `'2'`, `'3'` 및 기존 숫자 응답을 변환합니다. 회원 직접 취소 `'4'`는 매니저 취소 목록에 넣지 않습니다. 서버 조회 실패는 빈 목록으로 감추지 않고 재시도를 제공합니다.

## 취소 실행 연결 조건

`PATCH /match/manage/cancel/{m_id}`는 JSON `g_code` 문자열, `r_date` 날짜, `rs_time` HH:mm, `r_c_category` 숫자 1~3을 요구합니다. 공통 통신 계층에 PATCH와 client 주입을 추가하고, 중복 제출 차단·실패 시 선택 유지·성공 후 관련 목록 무효화를 Mock으로 검증했습니다. 실제 금액 환불을 수행했다고 표시하지 않습니다.

현재 `/match/operations`의 목록 응답에는 `g_code`가 없고 조회 SQL에도 취소 예약 제외 조건이 없습니다. 프론트는 구장 코드와 유효한 경기 일시가 제공되는 경우에만 취소 실행을 연결하도록 방어하며, 현재 응답에서 버튼을 억지로 활성화하거나 경기 코드를 임의 분해해 사용하지 않습니다. 운영 API의 구장 코드 응답·취소 예약 처리 보완 여부는 사용자 선택 대기입니다. 취소 후에도 기존 운영 API에 취소된 경기가 남을 수 있으므로 실행 연결 완료로 보고하지 않습니다.

## 유지한 제한

신규 팀 경기 API는 본사용이며 로그인 매니저로 제한하는 필터·서버 권한 계약이 없습니다. 매니저 `팀경기매치`는 기존 사용자 선택대로 보류 상태를 유지했습니다. 전체 팀 경기와 팀장 연락처를 받아 프론트 필터만으로 본인 전용 조회라고 표시하지 않습니다.

## 검증

HTTP MockClient와 provider override로 팀 경기·취소 사유·역할별 조회 URL·실제 PATCH 메서드·JSON·오류와 중복 제출을 검증했습니다. 실제 서버·실제 DB에 대한 동작 검증은 실행하지 않았습니다. 기존 작업 파일과 로그인·경기 진행·교육·신고 기능은 유지합니다.
