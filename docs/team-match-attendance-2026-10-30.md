# 팀매칭 예약자 출석·경기 운영

작성 일 : 2026-10-30 / 작업자 : 양태건

## 적용 기준

- 담당 매니저에게 배정된 성사 팀매칭만 접근한다.
- 같은 구장·날짜·시작/종료 시간의 유효 구장대여 예약자를 조회한다.
- 고객의 현재 소속팀이 홈/원정인 예약자만 포함하며 취소 예약·탈퇴 고객을 제외한다.
- 중복 예약은 회원별 한 명으로 표시한다. 전체 팀원을 출전자로 추가하지 않는다.
- 예약 명단이 없거나 한 팀만 예약했으면 없는 회원을 보충하지 않는다.
- 팀장 한 명의 대여 예약만 저장된 경기는 그 예약자만 조회된다.

## 흐름

내 매치에서 팀매칭 선택 → 전원 출석/개별 출석·결석 → 고정 홈·원정으로 직접 시작 → 전체 화면 기록 → 종료·결과 확인 → 팀매칭 결과 등록.

- 전원 출석·결석을 확인하고 양 팀에 출석자가 있어야 시작한다.
- 팀 설정 화면과 인원 차이 1명 제한을 적용하지 않는다.
- 팀매칭 경기 시작에는 실력매칭의 출석률 70% 조건을 적용하지 않는다. 팀 경기 결과 등록의 결석자는 차감하지 않지만, 노쇼 취소 확정 시에는 아래 패널티 정책을 적용한다.
- 시작 이후 예약 명단이 바뀌면 임의로 출전자를 바꾸지 않고 409로 안내한다.

## API·저장

- GET/POST `/match/team_operations/{code}` : 매니저 Bearer 인증, version 검증.
- 기존 `/match/manager/teams/{code}/roster`도 같은 예약 명단을 반환한다.
- 출석과 부상은 기존 `c_result_record`를 사용한다.
- 결과 등록은 기존 팀·개인 점수 계산 함수를 공유하고 같은 트랜잭션에서 저장한다.
- 기존 출석 행은 결과 UPDATE로 재사용하여 부상 기록을 보존한다.
- 팀 경기 행 잠금·기존 결과 검사로 결과·점수 중복 반영을 막는다.
- DB 스키마 변경 없음. 실제 DB에 테스트 쓰기·마이그레이션을 실행하지 않았다.
- 경기 진행 상태·타이머·개별 이벤트는 기존과 같이 서버 메모리에 보관한다. 서버 재시작 후 미등록 진행을 유지한다고 보장하지 않는다.

## 종목 보완

`team_create.c_category`는 실제 DB에서 개설일/폐지일을 뜻한다. 팀 종목 조회·결과 등록은 개설 회원의 `customer.c_prefer_stock`을 사용하도록 바로잡았다.

## 검증

Mock 기반 Python 테스트로 명단 SQL·담당자 범위·고정 팀·직접 시작·결과 등록·롤백·중복 제외를 검증한다. Flutter Mock 테스트로 팀별 예약자 표시·출석·팀 설정 생략·전체 화면 기록을 검증한다.

실제 DB 읽기 전용 조회에서는 대상 경기의 홈 6명·원정 6명(총 12명)을 확인했다. 실제 서버의 출석·경기 결과 저장은 DB 쓰기를 피하기 위해 실행하지 않았다.

## 팀매칭 경기 취소

- 출석 화면에서 기존 사유 선택 창(시설 문제/우천·기상악화/노쇼 및 환불)을 연다.
- `PATCH /match/manage/cancel/{m_id}`에 기존 구장·날짜·시작 시간·사유와 `team_code`를 함께 보낸다.
- 팀매칭 요청은 매니저 Bearer 인증과 실제 경기 담당자·구장·일시를 검증한다.
- 팀 경기 잠금·메모리 상태 확인·최종 결과 검사를 통해 시작/결과 등록과 취소가 동시에 처리되지 않게 한다.
- 노쇼 조회는 실력매칭 코드 대신 숫자 팀 경기코드를 사용한다. 중복 출석 행은 예약 수를 부풀리지 않게 DISTINCT로 조회한다.
- 취소 사유별 인원 조건은 기존 매니저 취소 API를 따른다.
- 취소 성공 시 예약 상태·결제 기록 처리와 기존 취소 이력 계약을 유지하고 진행 캐시를 제거한다. 실제 PG 환불을 실행하는 기능이라고 해석하지 않는다.
- 앱은 성공 이후 일정·선택 날짜의 매치·상세·취소 내역을 갱신한다. 내 매치 내부 화면에서는 대시보드를 pop하지 않는다.
- Mock 테스트로 요청의 팀 코드, 실패 후 재시도, 성공 시 갱신 경로, 시작 후 취소 차단을 검증했다. 실제 예약 취소·결제 기록 삭제는 실행하지 않았다.

## 실력매칭·팀매칭 결과 페이지의 취소 내역

- 두 결과 페이지 안에 `경기 결과 / 취소 내역` 전환을 추가한다. 종목 필터는 두 목록에 적용한다.
- 기존 `GET /match/manage/cancel/{m_id}`에 선택 쿼리 `kind=pickup|team`, `e_code`를 추가했다. 기존 필터 없는 조회 계약은 유지한다.
- 유형별 조회는 매니저 인증과 요청 담당자 ID를 검증하고, 기존 담당 구장의 취소 예약을 조회한다.
- `reservation_category=1`은 실력매칭, `2`는 팀매칭/구장대여 예약으로 분리한다. 회원 직접 취소 사유는 기존 매니저 취소 조회와 같이 제외한다.
- 예약 행을 구장·경기 날짜·시작/종료 시간·취소 사유별로 묶고 취소 인원·취소 일시·예약 회원을 반환한다.
- 소속팀은 `customer.c_team`의 현재 값으로 표시하며 취소 당시 소속으로 단정하지 않는다.
- 한 경기의 종목 정보가 섞여 있으면 임의 종목을 부여하거나 일부 회원만으로 취소 인원을 표시하지 않는다.
- 취소 성공 시 유형별 목록 캐시도 무효화한다. 조회 실패는 빈 목록으로 숨기지 않고 재시도를 제공한다.
- 새 테이블·컬럼은 추가하지 않았고 실제 DB 데이터는 수정하지 않았다.


## 취소 사유·노쇼 취소 패널티 정책

- 코드 1의 사유를 시설 문제로 변경하고 정원에 따른 취소 제한을 제거한다. 시설 문제·우천 취소는 점수를 차감하지 않는다.
- 코드 3(노쇼 및 환불) 취소가 기존 조건에 따라 확정될 때만, 결석으로 확인된 회원에게 최대 -30점을 적용한다. 출석/미확인 회원은 제외한다.
- 실력매칭과 팀매칭 모두 해당하며, 숫자 팀 경기코드와 실력매칭 코드를 구분한다.
- 취소 대상 예약 ID로 범위를 한정하고 기존 전·후 점수가 모두 NULL인 결석 기록만 처리한다. 이미 반영된 경기의 재차감은 하지 않는다.
- 기존 최저 1000점 규칙을 유지한다. 기존 비정상 하한 미만 데이터가 있어도 패널티로 점수를 올리지 않는다.
- 점수 차감·전후 이력 저장·결제 기록 처리·예약 취소를 같은 트랜잭션에서 처리한다. 실패 시 모두 롤백한다.
- 취소 창에서 사유에 따라 점수 차감 여부를 안내한다. 출석 화면에서 열면 현재 결석 확인 인원도 안내한다.
- 기존 코드 1 이력도 새 사유명인 시설 문제로 표시된다. 회원 앱이 별도 사유명 매핑을 사용하면 같은 코드명 변경을 반영해야 한다.
- 실제 DB 스키마·데이터는 직접 변경하지 않았으며 실제 예약 취소를 검증용으로 실행하지 않았다.

## 결과·취소 내역의 경기일 필터

- 실력매칭·팀매칭 결과 페이지에 달력 선택, 이전/다음 경기일, 오늘, 전체 기록을 추가했다.
- 선택한 경기일은 경기 결과와 취소 내역 탭에 동일하게 적용한다. 취소 일시와 경기 일자를 혼동하지 않는다.
- 기존 전체 조회 API 응답을 프론트에서 필터하므로 날짜 전환마다 같은 목록을 다시 요청하지 않는다. 백엔드·DB 변경은 없다.
- UTC 일시는 한국 날짜로 비교한다. 실제 경기일이 없는 결과를 등록일로 추정하여 날짜별 목록에 넣지 않으며, 해당 기록은 전체 기록에서 확인할 수 있다.
- 날짜·계정·매칭 유형을 바꾸면 이전 상세 선택을 초기화한다.
- Mock 검증: 실력/팀 결과와 취소의 날짜 이동·달력·오늘·전체 복귀, 취소일과 경기일 구분, 미기록 경기일·한국 시간 변환.

## 취소 예약 회원의 패널티 표시

- 유형별 취소 조회에 같은 구장·회원·경기코드의 점수 이력을 연결한다. 팀 경기코드는 `team_match`의 경기 날짜·시작 시간과 확인한다.
- 취소 시각 이전의 마지막 기록만 조회하여 이후 재예약/다른 경기의 점수와 섞이지 않게 한다.
- 노쇼 취소의 결석 회원에 한해 저장된 전·후 점수와 실제 차감액을 표시한다. 현재 점수나 기본 1500점에서 추정하지 않는다.
- 화면 예: 결석 / 노쇼 패널티 -30점 / 1500점 → 1470점. 하한에 걸린 경우 실제 -10점·0점을 그대로 표시한다.
- 출석자는 패널티 없음, 이력이 없거나 출석 상태를 확인할 수 없으면 패널티 기록 없음으로 구분한다.
- 실제 DB는 읽기 전용으로만 확인했고 차감 데이터를 추가·변경하지 않았다.
